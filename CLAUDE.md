# بيت العائلة (Household Hub) — project brief

A private family app for 3 people (the owner, his sister, their mother) to manage chores, a shopping/restock list, and household complaints with an AI-assisted **private mediation** flow. Arabic, RTL, designed so an older, non-technical person can use it. Built and iterated with Claude; this file is the context Claude Code needs.

## Stack (deliberately minimal — keep it that way)
- **One static page**: `index.html` (vanilla JS, no framework, no build step). CSS/JS inline, with one deliberate exception: `qrcode.min.js` (vendored kazuhikoarase/qrcode-generator, MIT) is a plain sibling static file loaded via `<script src>`, not inlined — kept separate so the ~20KB minified blob doesn't clutter the main file. Still zero build step, still fully offline-capable.
- **PWA**: `sw.js` + `manifest.json` + icons → opens offline after first visit. `sw.js` also handles Web Push (`push` / `notificationclick` listeners).
- **Backend**: Firebase Firestore (offline persistence on) + Anonymous Auth. Config is in a small `<script>` block near the top of `index.html` (`window.FIREBASE_CONFIG`). Data lives under `families/{familyCode}/…`. The family code is a shared secret each phone gets via QR scan (primary path, `sCloud()`) or manual entry (fallback); it is **never** in the repo.
- **AI**: `netlify/functions/ai.js` proxies to free models on **OpenRouter** (`process.env.AI_API_KEY`, an OpenRouter key set manually in Netlify → Site configuration → Environment variables — do not remove it, nothing auto-injects it). The function translates the Anthropic-shaped request/response the frontend uses to/from OpenRouter's OpenAI-compatible format, so `index.html`'s `callAI()` is unchanged. max_tokens capped at 600 (set client-side; the receipt-scan vision call asks for 900 since a receipt's item list is longer). Frontend falls back to a key shared via Firestore settings, then a per-phone key (direct Anthropic call), if the function is absent.
  - **Model lists are env vars, not code.** `TEXT_MODELS` and `VISION_MODELS` (comma-separated) override the defaults in the file. A free slug can be retired by OpenRouter without warning — `deepseek/deepseek-v4-flash-0731:free` died in use — and this is what makes a swap cost **zero deploy credits**: set the env var in Netlify to a `:free` slug from https://openrouter.ai/models?max_price=0 and the next invocation picks it up. Vision is a separate list because receipt scanning sends an image and most text-only free models reject an image payload; requests carry `vision:true` to select it.
  - **`:free` only, enforced in code.** Any slug not ending in `:free` is dropped before a request is made, and the drop is reported rather than silent. This matters because OpenRouter's own 404 body says *"The paid version is available now - use this slug instead: …"* — following that hint, by hand or by pasting it into the env var, would start billing the account.
  - **Rate-limited ≠ retired.** A `429` means the free quota is spent, not that the model is gone — conflating the two sends you hunting for a replacement slug when the model is fine. The proxy retries a `429`/`502`/`503`/`529` **once** after ~1.2s (a burst limit usually clears; retrying more just burns the same quota) and never retries a `404`, since a retired model will not come back. The error then says RATE LIMITED explicitly, and if only one model is configured it says so — a single-entry list has nothing to fall through to, which is the whole reason to list several `:free` slugs **from different providers**. OpenRouter also ties the free-tier daily cap to whether the account holds credit; free models still cost nothing, the balance just raises the cap.
  - **Provider pinning and temperature** (both env vars, both zero-deploy). One model is served by several upstream providers, and they differ in quantisation and defaults, so wording and JSON reliability drift between them. `PROVIDER_ORDER` (comma-separated provider names, exactly as OpenRouter spells them) sets the preference order. `PROVIDER_STRICT=1` also forbids any fallback — maximum consistency, minimum availability: when the pinned provider is limited the request simply fails, and the rate-limit error says the pin is why. `AI_TEMPERATURE` (default **0.3**) was previously unset, meaning each provider's own default of roughly 1.0; since most calls here demand strict JSON, a low value steadies both tone and parsing. The success response and `GET` both report the serving `provider` and `model`, and ⚙️ المزيد ← 🤖 المساعد الذكي shows them after a passing test — you cannot sensibly pin a provider before you can see which one you are getting.
  - **Every attempted model is reported.** On total failure the error names each model and what it said (`slug → status: message`), because returning only the last model's error hid why the earlier ones failed and made a dead free tier look like a fault in whichever model was last. When all of them look retired the message also spells out the env-var fix. `GET /.netlify/functions/ai` returns the live config (`textModels`, `visionModels`, `ignoredNotFree`), and ⚙️ المزيد ← 🤖 المساعد الذكي shows it when a test fails — so a retired model is diagnosable from the app, without reading Netlify's logs.
- **Push notifications**: `netlify/functions/check-reminders.mjs` is a Netlify Scheduled Function (cron `*/30 * * * *`, configured inline via `export const config = {schedule}` — note scheduled functions need the modern `export default (req) => Response` shape, not the classic `exports.handler` style `ai.js` uses) that sends Web Push via the `web-push` npm package for two things: (a) a **scheduled** chore due today with an unmet assignee, and (b) a **mediation case waiting on someone** — `stage:"sent"` and not yet `openedAt` notifies `about`, `stage:"b_ready"` notifies `from`, keyed per round in a server-written `notified:{"sent:1":true}` map so each round notifies once. Case pushes are deliberately **content-free** (no summary, no title): a push preview shows on a lock screen other people in the house can see, and that flow is built on privacy. Its `isDueToday()` must mirror the client's, including `"anytime" → false`; without that an as-needed chore would be pushed every single day. As-needed chores (rotating or not) are intentionally never pushed — nobody is "due", so a periodic turn reminder would just be spam, using Firebase Admin SDK (`firebase-admin`) to read Firestore server-side across all families. Needs two secrets set in Netlify (never in the repo): `VAPID_PRIVATE_KEY` and `FIREBASE_SERVICE_ACCOUNT` (full service-account JSON). The matching public VAPID key is safe to be public and is embedded in `index.html` as `VAPID_PUBLIC_KEY`.
- **Hosting**: Netlify, linked to this GitHub repo. Push to `main` = production deploy.

## Hard constraints — do not break
1. **Private chat threads never leave the phone.** `cases[].threadA` / `threadB` live only in localStorage. Only `neutralSummary`, `suggestions`, `proposedResolution`, `noteFromSender`/`noteFromResponder`, and stage go to Firestore (`cases` collection).
2. **The AI's own words are tamper-proof; consent-to-send still gates delivery.** `neutralSummary`/`proposedResolution` are shown read-only once generated — a user can no longer rewrite them (this was a deliberate change from v2; previously they were editable). A user may attach a separate, clearly-labeled optional note (`noteFromSender`/`noteFromResponder`) alongside it — shown to the recipient as a distinct block, never merged into the AI's text — to flag a correction or add context. The person still explicitly taps send/doesn't; nothing reaches the other party automatically. The AI defaults to strict neutrality (no declaring who is "right"), but `CORE_GUARDRAILS` carries one narrow, evidence-gated exception: it may name a specific unfairness *only* when logged app facts or clear mutual admissions support it — never based on who argued more persuasively or insistently (see the guardrail's own anti-manipulation clause).
3. **Citation whitelist.** `QURAN_FRAMEWORK_ITEMS` is a small, source-verified list. `flagUnverifiedCitations()` appends a ⚠️ to any ayah/hadith/surah reference not in it. Never add entries without verifying the exact text against two sources; never let the model cite from memory.
4. **`CORE_GUARDRAILS`** (in `index.html`) always prefix every system prompt: no diagnosing people, no declaring who is "right" by default, facts only from logged data, equal respect, de-escalate. User-editable persona/book rules are layered *after* it, never instead of it.
5. **User text goes into prompts as fenced data** via `fenced()` — never string-interpolated into instructions (prompt-injection guard).
6. **No secrets in the repo.** Firebase web config is fine (it's a public identifier), as is the public VAPID key; family code and any API/private key are not.
7. **Elderly-friendly UI**: base font 19px, tap targets ≥ 44px, one idea per screen, Arabic labels, minimal jargon. Don't add a framework, a build step, or clever UI for its own sake. QR scan/display is the primary family-linking path specifically because it beats typing a long code on this audience; manual entry stays as the fallback for unsupported devices (`BarcodeDetector` — notably not on iOS Safari).
8. **Errors must be visible** — never silently fall back. Use `toast()` / red `.bubble.err` / `errorCard()`.

## Netlify credits — this matters
Free plan = 300 credits/month, hard cap; at 0 the site pauses. **Each production deploy = 15 credits.** AI use does **not** cost Netlify credits (it goes through OpenRouter's free tier via `AI_API_KEY`, not Netlify's own AI Gateway). The scheduled reminder function runs every 30 min regardless of activity — this is normal Netlify Functions usage, not a credit-per-deploy cost, but keep an eye on it if usage patterns ever change. Batch code changes into one push where possible: test locally first (open `index.html` in a browser for most UI/logic — camera scanning, push subscription, and Firestore all need a real `http(s)` or `localhost` origin, not `file://`), push once. Avoid pushing trivial tweaks.

## Data model (Firestore + localStorage mirror)
- `meta/settings`: `{members:[{id,name}], profiles:{memberId:{speak,values,wants,triggers,calm,note}}, aiKey, updatedAt}`
- `chores/{id}`: `{id,title,assignee(memberId|"anyone"),freq("daily"|"days"|"once"|"anytime"),days:[0-6],rotation:[memberId,…],log:{"YYYY-MM-DD":{by,at}},remindedDates:{"YYYY-MM-DD":true} (written server-side by check-reminders.mjs),createdAt,updatedAt}`. `"anytime"` = as-needed/unpredictable: `isDueToday()` returns **false** for it so it never creates schedule pressure, but completing it still writes to `log` and counts toward the streak/stats. Listed in its own always-visible card on ☀️ اليوم, which also shows when it was last done and by whom — the thing you actually need to know for an as-needed job.
  - **Turn-based rotation** (as-needed chores only): `rotation` is an ordered list of ≥2 member ids; the add-chore form only offers it for `"anytime"`. A rotating chore is forced to `assignee:"anyone"` so it isn't pinned to one person. Whose turn it is is **derived** by `whoseTurn()` from the completion log — never stored as an index — because a stored counter would fight itself under last-write-wins merge, and deriving self-corrects when somebody covers out of turn (the person they covered for is still next). Anyone may still tap "سويتها" regardless of whose turn it is; the turn is shown, never enforced, per Owner's intent (no shaming).
- `restock/{id}`: `{id,name,qty,price,note,status("needed"|"bought"),addedBy,addedAt,boughtBy,boughtAt,updatedAt}`
- `complaints/{id}` (agreed outcomes only): `{id,from,about,title,description,status:"resolved",createdAt,updatedAt}`
- `cases/{id}` (mediation hand-off, summaries only): `{id,from,about,title,tag,choreId,choreTitle,stage,neutralSummary,suggestions,proposedResolution,noteFromSender,noteFromResponder,takeaway,sentAt,openedAt,round,rounds:[],updatedAt}`
  - stages: `draft_a → ready_to_send → sent → (other phone) received → b_ready → (back) awaiting_a → closed`
  - **Revisable until opened**: `openedAt` is stamped exactly once, the first time the recipient actually renders a `received`-stage case, and syncs back to the sender. While it is 0 the sender's `sent` screen offers "✏️ عدّل قبل ما توصل" (back to `draft_a`, threadA intact); once it is set, that button is gone. The cases listener also refreshes an unopened inbox copy in place when the sender revises, so B never reads a withdrawn version.
  - **Up to 3 rounds** (`MAX_ROUNDS`). Declining the proposed resolution archives the round into `rounds[]` (`{n,neutralSummary,suggestions,noteFromSender,proposedResolution,noteFromResponder,takeaway}`), clears the per-round fields, increments `round`, and returns to `draft_a` — `threadA`/`threadB` deliberately **survive** across rounds, only the per-round artifacts reset. At round 3 it stops and suggests talking face to face instead. `takeaway` is a ≤6-word label the AI returns alongside the summary/resolution; `roundsMapHTML()` renders the history identically on both phones.
  - `notified:{"<stage>:<round>":true}` is written **server-side** by `check-reminders.mjs` to avoid re-notifying; the client neither reads nor writes it.
  - `choreId`/`choreTitle` link a case to a chore (see **Chore ↔ complaint bridge**). When set, `choreFactsForCase()` fences the chore's dated record into the summary *and* the responder's prompt, and both phones see it on screen — so a chore dispute argues from the log rather than from how often someone *remembers* it happening.
  - `tag` is an optional free-text label set on the draft screen; `renderComplaints()` builds filter chips from the distinct tags. Manual, not AI-clustered — deliberately, so the family controls how their own sensitive data is categorized.
- `kudos/{id}` (peer-validated "what I did" log, اليوم tab): `{id,memberId,text,date,confirmedBy:{memberId:true},createdAt,updatedAt}`. Deliberately not tied to the chore streak/leaderboard — no counts or ranking surfaced, by design (see Owner's intent).
- `agreedRules/{id}` (standing house rules promoted from a resolved case, الشكاوى tab): `{id,text,sourceCaseId,sourceTitle,createdAt,updatedAt}`. Also fed into `buildJudgmentContext()` so the mediator is aware of prior agreements.
- `pushSubs/{id}` (Web Push subscriptions, one per phone that enabled notifications): `{id,memberId,endpoint,keys,createdAt,updatedAt}`. Consumed server-side only, by `check-reminders.mjs`; not part of the manual (no-cloud) export/import code.
- Merge rule everywhere: `mergeArrayById` = last-write-wins by `updatedAt`.
- Per-phone localStorage only (never synced): `hh_fontsize_v1` (UI text size), `hh_lastseen_v1` (the "since you last looked" mark), `hh_choretalks_v1` (private chore conversations — never synced), `hh_chorenudge_v1` (nudge snoozes).

## Chore ↔ complaint bridge
A missed chore can start a mediation case, in two directions. Both are gated on the **log**, never on someone's impression.
- `missedRecord(chore, days)` counts due-but-unmet days from *yesterday* backwards (today isn't missed yet), and **never earlier than `choreStartDate(c)`** — a chore cannot have been missed before it existed. Without that clamp a chore added today reads as missed on all 14 days of the window and trips the nudge immediately. `wasDue(c, ds)` pairs the clamp with `isDueToday()` and is what the calendar day view must use, or it marks past days as missed for a chore that did not yet exist. When a chore is younger than the window the UI says "منذ إضافتها" rather than claiming 14 days. A chore with no `createdAt` falls back to its earliest log date, then to today — unknown age is treated as new rather than accused retroactively.
- Only `nudgeable()` chores count — `daily`/`days` — since a `once` or `anytime` chore has no day it was supposed to happen on.
- **The person themselves** (`NUDGE_MIN_MISSES=3` misses in `NUDGE_WINDOW=14` days): a card on ☀️ اليوم offers a **private** talk, `openChoreTalkModal()`. The thread lives in `hh_choretalks_v1`, localStorage only, exactly like `threadA` — hard constraint 1 applies. The AI is told not to blame, not to assume laziness, and not to diagnose; it asks what got in the way and helps pick a practical way out. Nothing reaches anyone else unless the person taps "اقترح تعديل على العائلة", which creates a `ready_to_send` case (never `sent`) whose `threadA` *is* that private talk. "مو الحين" snoozes for `NUDGE_SNOOZE_DAYS`, stored in `hh_chorenudge_v1`.
- **Another member** (`startChoreCase()`): a "🕊️ تكلم عنها بهدوء" button appears on 🧹 المهام, but only on someone else's chore that already shows ≥3 misses. Pre-fills a case linked to that chore.
- **Why private-first**: an automatic "you missed your tasks, explain yourself" is exactly the shaming the Owner's intent rules out, and it would decide something about a person without their agreement. The nudge is therefore visible only to the person it concerns, and the consent-to-send gate is the same one the complaint flow already uses. Never make this broadcast without being asked to.

## UI conventions added after round 2
- **Undo, not confirm.** There are no `confirm()` dialogs left. A delete applies immediately — locally *and* in the cloud — and `deleteWithUndo()` offers "↩️ تراجع" in a toast that restores it (re-pushing to Firestore). Deliberately not a deferred delete: applying it for real means closing the app mid-undo can't resurrect the item. Confirm dialogs were dropped because a non-technical user learns to dismiss them reflexively, so they add friction without protecting anything.
- **Arabic-Indic numerals everywhere.** `ar()` converts `0-9 → ٠-٩` for every rendered count, price, total and day number; dates use the `ar-u-nu-arab` locale. Mixing `123` and `١٢٣` on one screen is the main thing that read as unpolished.
- **"من آخر ما فتحت" digest** on ☀️ اليوم: what *other people* did since this phone last had the app open. `seenSince` is captured **once at boot** so the list can't shift or empty while being read; the stored mark only advances on `visibilitychange→hidden` / `pagehide`. A first-ever run shows nothing rather than everything.
- **Text size** is a `--fs` CSS variable (17–28px, default 19) set from ⚙️ المزيد ← 🔤 حجم الخط. Constraint 7 targets an older user, so the 19px floor is a default, not a ceiling.
- **Per-person day view**: tapping a calendar day renders `dayDetailHTML()` — what each person completed and missed that day, grouped by person with their colour, plus a per-person tally. Future days show no misses. The block is scrolled into view on tap, since on a phone it renders below the grid.
- **Arabic plurals**: `timesAr(n)` handles 1 / 2 / 3-10 / 11+ (مرة / مرتين / مرات / مرة). Getting this wrong reads as broken to a native speaker.
- **Visual weight**: `.card.primary` (accent border) marks the one card that needs action — today's tasks, only while something is pending; `.card.quiet` dims the streak and leaderboard so they don't compete with it.

## Screens (bottom tabs)
☀️ اليوم (what changed since you last looked, my tasks today, as-needed tasks, streak + 16-week heatmap, weekly leaderboard, peer-validated "what I did" log) · 🧹 المهام (add chore, monthly calendar with per-person dots, all chores) · 🛒 التسوق (qty/price optional, running total, receipt scan, comma/و-separated multi-add) · 💬 الشكاوى (start private case, tag filter chips, inbox of received cases, agreed-rules log, resolved-complaints log) · ⚙️ المزيد (menu → profile, family/names via QR or manual code, notifications, text size, stats, AI, Quran framework, persona, book rules, manual sync fallback).

## Testing
Open `index.html` directly in a browser to test most UI/logic. The full case flow (draft → send → open → respond → counter-round → rounds map → resolve) is exercisable **offline** without Firestore by driving two separate browser profiles through the manual code-package path, with a stub that answers `/.netlify/functions/ai` — that is how round 2 was verified. Camera-based QR scanning, Web Push subscription, and the Firestore path all need a real `http(s)` or `localhost` origin — `file://` breaks relative-path script loading and secure-context APIs, so those specifically need `netlify dev`, a local static server, or the deployed site. There is no automated test suite; a quick manual smoke test used during development checked: add chore → mark done → calendar detail → streak → restock total → add/confirm a kudos entry → open case modal (all stages) → every settings sub-screen renders without an error card → QR display renders a real scannable pattern → notification permission flow degrades gracefully when denied/unsupported.

## Owner's intent (so changes stay on-purpose)
The goal is fairness that doesn't depend on who argues loudest: a dated, shared record; a mediator that can't be steered into taking sides except on clear, evidenced unfairness; and a process where nothing is decided about someone without their explicit agreement. Gamification (streaks, leaderboard) is welcome; anything that shames or ranks people's *character* is not — this is also why the "what I did" recognition log deliberately has no counts or comparison, only peer confirmation, and stays separate from the chore leaderboard.
